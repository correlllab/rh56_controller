# GGX 交互审核与 CB3 执行入口

已有满意抓姿、需要重复十个起点实验时，使用
[固定模板 × 十起点入口](ggx_ten_starts_zh.md)，不必每轮重新推理 GGX。

原有功能不是完整的 GGX generate → approve → real 一键流程：
`grasp_viz_ui.py` 的仿真／实机入口属于原 planner；GGX 原来只有生成器、
`preflight_ggx_ur5_table.py` 和手动填写的 `human_review.csv`。

新增 `tools/run_ggx_review.py` 复用这些 GGX 工具，串起：

拍摄 → 顶面编号确认 → 实测点云裁剪 → GGX 一次推理 → 按置信度逐个仿真 →
自动跳过预检失败项 → 打开通过项视频 → 人工批准／拒绝下一项。

## 实机模式：检查前移，批准的是 CB3 执行视频

`run_ggx_review.py --execute` 现在使用以下流程（不带 `--execute` 的离线审核保持不变）：

拍摄／选择目标 → GGX 排名与数值筛选 → 当前起点的 CB3 准备、控制器 IK/FK 和路径几何检查 →
播放 **CB3 已检查执行路径** → Enter 授权执行，`n` 换下一候选，`p` 重放，`r` 作废场景，`q` 取消。

不再先要求批准 UR5e 视频，也不生成该无人查看的视频；原数值筛选仍保留。
待审核候选另存 `execution_candidate_NNN.json`（`rh56_ggx_execution_candidate/v1`），
明确 `human_approved: false`、`executable: false`，不能伪装成旧版人工批准记录。
随后 `real_rank_NNN/` 保存实际 CB3 检查、视频和最终 Enter 绑定的文件哈希。
只有完整检查通过才显示运动批准提示；任何实际状态、配置或控制器错误仍中止。
明确的名义 CB3 IK／碰撞拒绝可跳到下一候选，但不把任意控制器异常当成普通候选拒绝。

第一次控制器连接前仍需一次 Enter，**只授权本次运行内候选的 RTDE 脚本启停／查询**，
不授权运动；`n` 翻页不会重复索取这个权限。退出后失效，不保存到下一次运行复用。
每个候选都需要自己的 CB3 视频 Enter；接受后不再重算 IK、几何或视频，
但仍做新图像的现场有效性核验、起点／零 TCP／状态和文件检查，再发送运动。
拍摄仍需要时间，因此这不是“按 Enter 立即运动”或“取消所有后续检查”。
运动速度、手部 raw speed/force、实时偏差／急停／保护停止监控均未更改。

新执行模式必须保留唯一的 CB3 执行视频；`--no-real-video` 会明确报错，
实验配置里的 `preview_videos: false` 不会关闭它。下文关闭“额外视频”的旧说明
仅适用于未启用新审核模式的独立实机入口。
零自动通过的人工碰撞查看仍然只供观察，Enter 不授权它进入实机。

继续已保存的 rank 53（仅在物体／相机／桌面／安装未变时）：

```bash
MUJOCO_GL=egl .venv312/bin/python tools/run_ggx_real.py \
  --approval artifacts/ggx_review_runs/20260911T194809_266833Z/summary.json \
  --execute --phase approach-only --checked-review --allow-high-force
```

此命令先检查，再显示 CB3 视频；运动 Enter 后仍核验现场，如有下述深度告警还需照片确认，
全部通过后才张手、移动、接近。不会闭合或抬升。
`--checked-review` 也可用于其他旧视觉批准记录；新生成的一键执行入口自动启用它。
本次开发只做离线验证，没有运行上述实机命令。

### 固定场景：跳过重复拍摄和场景核验

操作者明确保证从**原规划参考拍摄**到开始动作期间，物体位置／高度、相机、桌面和安装保持固定时，
可以显式使用 `--static-scene`。初始和最终均不再拍照，不做 RGB／深度场景一致性检查，
也不要求本轮先通过一次完整深度检查。
规划保留原参考场景的 3D 坐标，不因新深度噪声调整目标。
每次执行仍需确认，不是“曾经通过就永久有效”；本轮没有新的传感器证据来证明场景未变。

```bash
MUJOCO_GL=egl .venv312/bin/python tools/run_ggx_real.py \
  --approval artifacts/ggx_review_runs/20260911T194809_266833Z/summary.json \
  --execute --phase approach-only --checked-review --allow-high-force --static-scene
```

`run_ggx_review.py --execute` 也接受并转发 `--static-scene`；生成候选需要的首次拍摄／点云仍正常执行。
该选项必须与执行模式、CB3 视频审核一起使用，默认关闭，不写入实验配置作为永久开关。
原批准场景／候选文件的完整性检查不变，没有本轮相机拍摄和视觉门槛。

CB3 视频的 Enter 同时确认固定场景假设，不再额外增加确认。物体／安装变动或有新障碍时应取消，
重新拍摄规划。静态模式不会触发深度告警的额外照片确认。
初始和最终会明确显示 `scene_check skipped`，不会启动这两次相机采集。
物体位置、高度、隐藏障碍和安装是否未变完全依赖操作者现场确认，不能用于无人值守动态场景。

机械臂实际起点、零 TCP、状态／实时运动监控、控制器与碰撞预检不变。
报告明确保存 `scene_policy: operator_fixed_reference`、`static_scene_confirmed`、
`capture_skipped: true`、`checked: false`、`rgb_checked: false` 和 `depth_checked: false`。
不伪造图像时间或视觉通过结果；没有新图像，因此本模式没有图像有效期判定。
默认不带此参数时仍执行完整初始和最终 RGB-D 检查。

之前仅跳过最终深度，导致 `20260911T204611_691955Z` 又在初始阶段被拒绝；该行为已修正。

开发没有连接或移动实机。

### 瓶子现场复查修正

当前为 `fixed_target_rgbd/v4`。先前 v2 保留固定像素比较和原 2px／3mm／5mm 判据，不注册或平移图像：

- 两幅图同样做 3×3 高斯降噪后比较外观，避免单像素噪声堆积成变化面积。
- 保留强边缘数量门槛，双向匹配到另一幅图的弱边缘；跨越 Canny 强阈值不再等同于轮廓大幅移动。
- 新出现的有效深度与本区域已经观测到的深度范围比较；不再用 1%/99% 裁掉少量已观测瓶肩表面。
- 深度比较仅增加 `1e-6 mm` 的浮点舍入容差，处理 float32 深度比例产生的 `5.000000237 mm`；
  不增大物理位移容差，也不填补深度空洞。

这是判据实现变化，不是整套视觉精度认证；弱纹理、遮挡、深度不足或明显变化仍停止。
保存照片的原始对比现在通过；额外合成的 3/8px 平移、5°旋转、4mm深度变化、遮挡、
深度丢失均拒绝。详见 `artifacts/ggx_lab/checked_review_scene_20260911_02/summary.json`。
rank 53 的保存起点通过离线名义 CB3 准备；它不等于实际控制器或动态抓取验证。

2026-09-11 的两次 `20:09` 运行仍因局部深度失败；v2 并未解决全部问题。
原参考连拍的左上区域本身已有约 6–8mm 的逐像素深度波动，不能当成可靠的毫米级位移证据。
v3 只用**参考连拍**确定质量区域，不从当前图的报错位置反向选择要忽略的点：

- 重用原 80% 有效帧中值算法，必须逐像素重建出已批准的目标 ROI 深度，否则拒绝。
- 参考帧相对中值的绝对偏差中位数 ≤1.5mm、P90 ≤2.5mm 才用于精细复查。
  这是将原 3／5mm 差异预算的一半留给参考重复性；属于待验证的质量假设，不是统计置信界。
- 至少一半参考有效点需可靠，且有效对比区域仍须覆盖三行三列、至少四格。
  可靠区域后来丢失深度仍拒绝，不能动态改成“不可靠”以放行。
- 原已不可靠区域不提供毫米级位移结论；RGB 检查和明显新深度表面检查仍覆盖那里。
  不补洞、不改点云、不修正目标位置，也不将未知区域宣称为无障碍。
- 原始参考帧及其相机元数据加入文件哈希，初次检查与最终 Enter 后复查不能替换。
  新审核记录直接包含这些文件；旧审核在本次运行读入并绑定，仍需当前 CB3 执行确认。
  声明为连拍却缺失／损坏原始帧时直接报错；真正的旧单帧输入保留严格旧检查，不自动绕过。

此参考保留 10,354／13,229 个深度点（78.3%），八格参与精细检查；两次 `20:09` 和先前
`19:51` 保存数据使用同一质量区域。离线回归记录位于
`artifacts/ggx_lab/scene_v3_20260911_01/regression/summary.json`，同时输出 `summary.csv`。
回归脚本 `artifacts/ggx_lab/scene_v3_20260911_01/audit.py --help` 只读保存数据，
包含平移、旋转、深度位移、遮挡和可靠区域深度丢失的合成反例；不连接硬件。
这不证明物体绝对静止或现场安全，也不能替代实机验证。抓取轨迹、模型、速度和力均未改动。
现场未动时继续使用上方原命令即可；不需要新增跳过检查的开关。

### 不稳定区域的新增深度：告警与照片确认（v4）

`20260911T201940_018376Z` 的八格稳定深度和 RGB 均通过，但参考时已不稳定的左上格
出现 660 个新增深度点，其中 95 个超出旧局部范围。因此 v4 将这一项改为**有条件的人工复核**，
不是 RGB-only，也不代表物体高度／位置已由照片验证。

- 仅当存在完整参考连拍，该格参考有效点 ≥20、可靠点 <20 时，空洞中新深度越界转为告警。
  该区域完全由参考数据决定；稳定区域的新表面、原有效点出现明显异常、可靠深度丢失、
  深度位移、RGB 位移／遮挡或整体证据不足仍直接拒绝，不能人工覆盖。
- 其他检查全部通过时才显示参考／当前原照片及相同坐标的目标放大图；橙框标出待复核格。
  操作者须查看照片并现场确认物体位置和高度、相机、桌面未变，没有新增遮挡／障碍。
  不确定时取消。Enter 只确认本次告警，不替代 RTDE 权限或 CB3 视频的运动批准。
- 首次／最终拍摄分别判断；首次接受不会自动接受最终新照片。没有告警就没有额外照片提示。
  `--no-open` 只关闭自动打开，仍打印图片路径并要求确认。其他输入、EOF、中断都不授权。
- 当前图片、参考数据、复核 SVG 和接受后的检查记录绑定哈希；复核期间或运动前变更会拒绝。
  记录保留 `automatic_passed: false`、告警数值及 `visual_confirmation_received`；
  离线检查未提供确认时仍是 `passed: false`，不会伪造“自动通过”。
- 最终照片的原 20 秒有效期包括检查和人工查看时间；超时停止，不重置拍摄时间，
  不自动重拍或重试运动。最后的机械臂起点／状态／零 TCP 核验仍保留。

此模式假设操作者可直接观察并核对已知、固定放置的物体，不适合无人值守或未知动态场景。
既有点云、抓取轨迹、模型、速度、力和控制器／碰撞检查未改动。

`audit.py --help` 位于其上一级目录。该回归不提供人工确认，也不连接硬件。

## 新场景用法

### 先张手复位，再摆放／重新感知

盒子已移动时，不要接着运行旧的 `--approval`。对当前直立糖盒，可运行：

```bash
MUJOCO_GL=egl .venv312/bin/python tools/run_ggx_review.py \
  --capture-live --reset-first --dimensions-mm 40 90 176 \
  --background artifacts/tabletop_background/empty_20260909_01 \
  --execute --real-phase grasp-lift --allow-high-force
```

流程：

1. 只读当前UR状态，显示复位目标和提示；Enter明确允许本次控制脚本启停、预检、张手和复位。
2. 预检通过后张手，按现有GGX抬升距离垂直上退80mm（保持姿态），再以一条MoveJ返回
   `artifacts/vision_pick_start/start_pose.json` 保存的拍摄起始位。这里的base不是关节回零。
   若已经在起始位，仍检查张手姿态的桌面间隙，但不发送多余机械臂运动。
3. 到位并断开控制连接后暂停。重新摆好物体，确认人员离开运动区，再按Enter才启动相机。
4. 新拍摄 → 选择目标 → 新GGX推理 → CB3／控制器检查 → 执行视频审核 → 抓取／抬升。

`--reset-first`本身是明确的复位动作开关，只能与`--capture-live`组合，不能带旧图像或旧审核。
去掉`--execute`仍可复位并拍摄／审核，但不会接续抓取；不带`--reset-first`的原命令行为不变。
复位失败、取消或断开连接出错都会停止，不进入感知，也不自动重试或补动作。

复位前尚无新物体位置，因此**不使用旧物体模型来保证路径安全**：现场必须确认物体已有支撑、
张手不会掉物，张手／垂直上退／返回路径畅通。80mm是沿用的退开距离，不是通用物体净空保证。
检查仍覆盖零TCP、CB3 IK/FK与限位、连续路径采样、固定桌面和实时偏差／稳定等待；
不包含新物体／夹具、完整自碰撞或未知初始手形的张开扫掠。桌面上界取实测平面在已确认
固定包围范围内的最高高度，不随新物体改变。RH56仍只写不读，张手按原有等待时间处理。
按操作者最新要求，复位张手与抓取的raw force/speed都使用1000，不再把复位张手暗中降到100。
必须显式带`--allow-high-force`并在复位／最终运动提示各自按Enter；缺少该开关时在设备连接、
拍摄或推理之前停止。1000是协议档位，不代表已测得的力或速度；RH56没有反馈，等待时间不变。
机械臂复位与抓取保留原低速：直线0.01m/s、0.02m/s²，
关节0.10rad/s、0.20rad/s²。操作者澄清慢的是动作前的计算；此前误加的复位加速档已撤回，
不是以加快机械臂来解决计算等待。路径、全部本地几何检查和冻结cube流程不变。
连接控制器、预检、张手、两段运动均打印耗时，记录在`reset/summary.json`的`timings`。
预检另存`controller_preflight_timing`（`rh56_ggx_controller_preflight_timing/v1`）：
总耗时、各类控制器查询次数／耗时／异常数、其余耗时、已通过采样点数和FK复用次数。
其中`other_s`也包含读取机械臂状态与Python开销，不能直接称为碰撞计算耗时。
复位与抓取共用此计时；失败时也保留计数和耗时。控制器连接耗时在复位阶段单独记录。

首轮计算优化在**同一次静止预检内**复用完全相同关节值、显式零TCP的
控制器正运动学（FK）；不舍入关节值，不缓存IK、限位结论或碰撞结论，不跨运动／运行复用。

### 不复位，只拍摄／审核

在仓库根目录运行，下例是直立糖盒，尺寸顺序为短边、长边、高度（mm）：

```bash

  --capture-live --dimensions-mm 40 90 176 \
  --background artifacts/tabletop_background/empty_20260909_01
```

每次生成唯一的 `artifacts/ggx_review_runs/<UTC timestamp>/`，不覆盖或自动复用旧候选。
使用当前相机设置拍摄，不连接 UR5/RH56，也不会自动张手或返回扫描位。

## 为什么现在仍要填写尺寸

GGX 网络只接收裁好的点云，不需要人工尺寸。当前适配脚本仍用尺寸完成两项工作：
裁剪实际RGB-D物体点云（避免混入手、夹具和桌面）并核对所选顶面；在MuJoCo中建立
完整盒子的碰撞代理。当前点云仅包含可见表面，不能直接当作完整碰撞几何。
因此此入口仍需要 SHORT LONG HEIGHT；自动估计或通用分割属于后续工作。
